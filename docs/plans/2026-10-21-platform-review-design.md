# Platform review 2026-10-21 — Design: findings and remediation plan

> **Status:** proposed. One of four review plans produced on 2026-10-21 (design, organization, functionality,
> security). Baseline: `main` @ f243038 plus the uncommitted SharePoint-sharing work, which was not judged.
> "Design" covers both the **platform architecture** (Part A) and the **user-facing design** (Part B).
> Method: a read-only reviewer agent read the ADRs, architecture docs and the code they describe, ran the mock stack
> (`AUTH_MODE=mock DATA_MODE=fixtures`) and captured 36 screenshots in steel, daylight and contrast at 1280, 1440
> and 1920 px, then stopped it. The three High findings and the three top UX findings were re-verified by hand
> (code and screenshots). Sibling plans: `2026-10-21-platform-review-organization.md`,
> `2026-10-21-platform-review-functionality.md`, `2026-10-21-platform-review-security.md`.
> **Validated** against `feat/sqlite-on-pvc` @ 2c7103d (one SQLite file, one pod) on 2026-10-21 — see the next
> section; §4 is rewritten from it. The findings in §3 are kept as written; obsolete ones are marked.

## Validation against feat/sqlite-on-pvc (2026-10-21)

**Method.** Every finding was re-checked in the `fix/platform-review` worktree (identical to `feat/sqlite-on-pvc` @
2c7103d). `portal/apps/web` and every package except `config` are byte-identical to f243038, so Part B only needed its
citations re-checked; the API, scheduler, deploy and docs changed. Ran `tests/unit/engine/{resume,state}.test.ts` and
`tests/api/{run-queue,retention}-db.test.ts` (green), and two throwaway benchmarks on this host's disk (better-sqlite3,
WAL, `synchronous=FULL`, `secure_delete`): a `probe_results` purge and a 100k-event audit-chain walk. Paths below are
relative to `portal/` unless they start with `docs/`, `tests/` or `config/`.

**What changed overall.** Two findings are obsolete (D-22, D-25), D-01 got worse (a second abort path), D-02, D-03,
D-04 and D-05 dropped a severity level because one process owns the database, the outbound limiter and the logs, and
the "transforms off the event loop" backlog item matters more: the one event loop now also runs the run worker, the
scheduler and every synchronous SQLite statement.

## 1. Verdict

**Architecture: sound, unusually well documented, operationally unfinished.** The identity topology (BFF token
custody, Read/Write app split, armed window with step-up, automation identity, sealed runner tokens) is implemented as
ADRs 001–003, 010, 011 and 014 describe. The content engine is genuinely generic: the renderer and engine branch only
on widget and template enums, never on a page key. The expression language is safe by construction (timebox, depth
and size limits, `$eval` off). Where it is unfinished is the operational edge: a worker restart cancels in-flight runs
for good, retention purges are unbounded over unindexed columns, and Microsoft throttling is managed per process with
no shared budget, no jitter and no per-call log lines from the worker or scheduler.

**User-facing design: distinctive, coherent and accessible; layout economics on laptop screens are the weak spot.**
Tokens only (`pnpm guard` clean), status is always icon plus label, ember is used strictly for write mode, every
state (loading, empty, error, not-found, public problem) exists with copy that says what happened and what to do, and
40 of 64 component test files run axe. The weak spots are structural: the inspector drawer covers the list at every
common width, list pages put the first row below the fold on a laptop, and small-count charts draw fractional ticks.

## 2. Keep doing

- The engine as a pure core with ports (`portal/packages/engine/src/ports.ts`): RunStore with compare-and-set,
  Clock, IdentityResolver, OutboundPort, RunnerPort, Notifier. Step checkpoints and `idempotent: false → needs_review`
  on resume are the right primitives; D-01 is about using them on shutdown.
- Content versioning end to end: semver plus sha256 per definition, publish refuses an unbumped change, interactive
  calls run only the current version, the browser reloads on 409.
- Partial-data honesty: `truncated` flows from executor to widget note, and every panel carries a provenance footer
  (service · path · ms · live/cached).
- One error vocabulary: `ErrorState` always shows what happened, what to do, a code chip and a reference; failed
  sign-in and arm round trips land on a designed public page.
- The armed moment is the one piece of theatre and it works: ember rail, viewport ring, countdown, Extend/Disarm, and
  the final confirm is the only ember button.
- The playbook drawer explains risk, what you need (portal role, Entra role with PIM state, Graph permissions) and
  shows the dry run as numbered HTTP calls.

### D-01 · A worker restart cancels in-flight runs permanently (High)

**Evidence.** `portal/apps/api/src/runs/run-worker.ts:197-202`: `stop()` aborts every active run's controller.
`portal/packages/engine/src/engine.ts:1039-1041`: when the signal is aborted the step is closed `cancelled` and the
flow returns `cancelled`; the run ends `cancelled`. The sweep (`run-worker.ts:28-29`) re-queues only `queued|running`
rows. The engine already has an `interrupted → retried` path (`engine.ts:803-823`) for a record left `running` when a
worker stopped, and a `needs_review` outcome for non-idempotent steps, but the abort path never leaves a record
`running`, so that path is unreachable on shutdown. `docs/operations.md` › Upgrade restarts the worker on every deploy.
Verified by reading the code; not exercised with a live SIGTERM.

**Failure scenario.** A write playbook is at step 3 of 5 during a routine upgrade. The run ends `cancelled`,
half-applied, indistinguishable from a person cancelling. Same for the API when `RUN_WORKER_IN_PROCESS=true`.

**Remediation.**

1. Abort with a reason (`ac.abort(new ShutdownSignal())`). In the engine, treat shutdown differently from cancel:
   leave the step record `running` (checkpointed) or mark the run `interrupted`, so the existing resume path runs on
   the next worker.
2. Drain: on SIGTERM stop taking new jobs, wait up to `TimeoutStopSec` minus a margin for active steps to reach a
   checkpoint, then abort with the shutdown reason.
3. Make the sweep (or pg-boss retry) pick up `interrupted` runs.
4. Test (api project): "SIGTERM during a step resumes on the next worker; a non-idempotent step ends `needs_review`".

### D-02 · Retention purges are unbounded over unindexed columns (High)

**Evidence.** `portal/apps/api/src/housekeeping/retention.ts:110-115` (`schedule_runs`) and `:131-136`
(`probe_results`) are single `DELETE … RETURNING` statements, while the runs purge just above them is batched.
`db/schema.ts`: `schedule_runs.run_id` (ON DELETE SET NULL), `runs.schedule_id` and `probe_results.schedule_run_id`
have no index; `runs_status_idx` is single-column though list and retention filter on status **and** time;
`probe_results` is indexed on `(probe_key, ts)` only, but retention and the history series range on `ts` alone. The
services' pool has a 60 s `statement_timeout`.

**Failure scenario.** 82 probes on 15-minute sweeps produce about 8k rows a day. The first purge after the 35-day
window deletes about 280k rows in one statement; each deleted run triggers a sequential scan of `schedule_runs`. The
statement times out, is not retried for hours, and the backlog grows faster than it drains while the audit lock
contends with it.

**Remediation.** One migration: batch every purge like runs (2,000 ids per transaction, loop until empty); add
indexes on `schedule_runs(run_id)`, `probe_results(schedule_run_id)`, `probe_results(ts)`, `runs(status, created_at)`,
`runs(schedule_id)`, built `CONCURRENTLY` outside a transaction. Apply to both the dev and host databases.

### D-03 · Throttling and observability of Microsoft calls (High)

**Evidence.** `portal/apps/api/src/execution/outbound.ts:991-997`: each process builds its own `Limiter`.
`portal/packages/connectors/src/http.ts:171-179`: `Retry-After` is honoured exactly (capped 120 s) with jitter only
on the exponential path. No circuit breaker anywhere under `portal/`. `datasources/services.ts:102` emits the
`microsoft call` line only at `info`, but `worker.ts:34` and `apps/scheduler/src/main.ts:92` pass `warn`-level loggers.

**Why it matters.** API, worker and scheduler together can exceed the Graph budget docs/performance.md sizes for one
app; when Microsoft throttles, every waiting request retries on the same second; and the journal holds no
Microsoft-side trace of a write playbook or a scheduled sweep, so "troubleshoot by reference" holds for page loads only.

**Remediation.** (a) Now: `info` loggers for `onCall` in worker and scheduler (one line each); ±20 % jitter on
`Retry-After`. (b) Next: a shared budget through Postgres (small token bucket per service or advisory slots), or at
least `OUTBOUND_CONCURRENCY` divided across roles by config; a per-service breaker (open after N consecutive 429/503,
half-open probe). Needs a short design note because it interacts with the performance sizing.

### D-04 · Production hardening fails open on `NODE_ENV` (Medium)

**Evidence.** `portal/apps/api/src/config.ts:80` defaults `NODE_ENV` to `development`; the production-only checks
(`config.ts:259-285`: no mock auth, database required, `TRUST_PROXY` must name proxies, database TLS, https base URL),

(`portal/deploy/systemd/system/adminforge-api.service`) sets no `NODE_ENV`; it relies on the owner's drop-in.

**Remediation.** Refuse to start when `AUTH_MODE=entra` and `NODE_ENV` is not explicitly `production` (or derive
production from `ADMINFORGE_ENV_FILE` pointing outside the repo), and set `Environment=NODE_ENV=production` in the unit
templates. Same `superRefine` change as D-25: validate `RUN_WORKER_CONCURRENCY ≤ DATABASE_POOL_MAX − 3`.

### D-05 · Audit log scaling (Medium)

**Evidence.** `audit/writer.ts:112-130`: `pg_advisory_xact_lock` per append, tail read by `seq desc limit 1`;

external-anchor item.
