# Platform review 2026-10-21 — Security: findings and remediation plan

> **Status:** proposed. One of four review plans produced on 2026-10-21 (design, organization, functionality,
> security). Baseline: `main` @ f243038 plus the uncommitted SharePoint-sharing work (not assessed).
> Scope: the product — code, content engine, provisioning logic, the design of its own app registrations, CI and
> supply chain, and the deployment artifacts in the repo. Not the tenant's hygiene.
> Method: a read-only reviewer agent read the API (auth, sessions, request policy, outbound executor, runs and
> approvals, schedules, audit, SSRF paths, secrets) end to end, with four sub-reviews (runner, CI/deploy/CLI, web
> client, expression engine) that confirmed each path by reading it in full or by running a throwaway `tsx` probe;
> `pnpm guard` and `pnpm audit --prod` were run; the live API was touched only for `GET /healthz` and `/readyz`
> headers. The four new Medium findings were re-verified by hand. Every finding is CONFIRMED (code path read in
> full or reproduced) or PLAUSIBLE (with what would confirm it). Sibling plans:
> `2026-10-21-platform-review-design.md`, `2026-10-21-platform-review-organization.md`,
> `2026-10-21-platform-review-functionality.md`.
> **Validated** on 2026-10-21 against `feat/sqlite-on-pvc` @ 2c7103d (one SQLite file on a PersistentVolume, Kubernetes
> only): see the next section. §4 follows the validation; §1–§3 keep the original wording (obsolete findings are
> marked).

## 1. Verdict

**Strong for an internal admin tool. No Critical or High finding. The security model in SECURITY.md is implemented
as described, and its known-gap list is honest.** The usual gaps of this class of tool are absent by construction:
no token reaches the browser, there is no generic write proxy, CSRF is enforced on every non-safe `/api` method,
outbound SSRF is bounded by allow-lists and pinned DNS, and errors never carry raw bodies. The expression sandbox
resisted every escape, prototype-pollution and regex-from-data attempt the reviewer tried. `pnpm guard` passes
14 / 14. `pnpm audit --prod` reports two low advisories (dompurify via monaco-editor) that data cannot reach.

The new findings are hardening and defence-in-depth gaps, not escalation paths: production-only controls hinge on
a `NODE_ENV` that nothing in the unit files sets; the publish-time injection lint misses user data wrapped in a
function or alias; a hostile character reference in tenant text can blank a page; datasource headers can override
`Authorization`; and the read-only PowerShell policy does not inspect file-redirection operators. Each is a small
fix with a named regression test.

## 2. Controls verified as working (keep)

- **Sessions and sign-in.** PKCE S256, single-use `state`, browser-bound round trips compared in constant time,
  nonce / `tid` / `oid` / guest / role checks at callback, fresh session id on login, `__Host-` cookie in production,
  idle and absolute expiry, roles re-read every five minutes and fail closed after fifteen, `invalid_grant` ends the
  session. The worker runs the same role check before delegated steps.
- **Arming.** CSRF plus Operator, `prompt=login` with `max_age=0`, callback bound to the starting session, same `oid`,
  `acrs` when `WRITE_AUTH_CONTEXT` is set, `auth_time` within 300 s or refused, minutes capped, one extension. Write
  tokens exist only while armed.
- **Outbound.** Default-deny policy evaluated on the declared path and again on the path exactly as fetch sends it;
  `cleanPath` refuses dot segments, encoded slashes, backslashes and control characters; `$batch` sub-requests judged
  one by one; `READ_POSTS` anchored and read-only; `declaredWrite` set only by the engine for `mode: write` steps;
  nextLink origin pinned; cursors HMAC-sealed; protected objects enforced even when Graph is unreadable.
- **Separation of duties.** Approvals refuse the initiator, the requester and the beneficiary; need the approver's
  roles, the playbook's roles and an armed session when later steps write; manual steps answered only by the person
  they wait for; previews single-use with the typed value never echoed; write-capable schedules need a second
  person at enable and again at fire time, bound to the definition hash and playbook fingerprint.
- **Web.** No `dangerouslySetInnerHTML`, `innerHTML`, `srcdoc` or `eval` anywhere; Markdown is a hand-written subset
  that builds React elements; CSV/XLSX formula characters neutralised; CSP `script-src 'self'` observed live with
  HSTS, `frame-ancestors 'none'`, nosniff, no-referrer, Permissions-Policy, COOP and CORP.
- **Secrets and audit.** Show-once secrets sealed and session-bound with a five-minute TTL; `redact: true` masked in
  views, audit and events; audit appended under an advisory lock with a hash chain and made append-only by database
  triggers; the services' role is checked at start-up and refused in production if over-privileged; logs strip
  query values, auth codes, cookies and the CSRF header.
- **Runner.** Three HKDF keys from one shared secret, HMAC over timestamp, method, path and body hash, ±60 s window,
  replay cache, tokens sealed per job and delivered on stdin only, every output line redacted, scripts resolved by
  path plus SHA-256 on the runner's own disk, parameters bound as JSON never interpolated, single-use workers with
  process-group kill.
- **Supply chain and host.** Actions SHA-pinned with `contents: read`, frozen lockfile, install scripts opt-in,
  system units with `ProtectSystem=strict` and empty capability sets, backups that refuse plaintext and exclude
  sessions, token cache and admin files.

### 3.1 New Medium findings

**S-01 · Production hardening is opt-in through `NODE_ENV`** (same defect as design D-04)
`portal/apps/api/src/config.ts:80` defaults `NODE_ENV` to `development`; `config/example.env:13` ships
`NODE_ENV=development`; no `Environment=NODE_ENV` in any unit template under `portal/deploy/systemd/`;
`portal/deploy/README.md:203` tells the operator to add it in a drop-in. Controls that key off it: HSTS (`app.ts:221`),
the `__Host-` cookie name (`auth/session-plugin.ts:22-23`), refusal of mock auth, `TRUST_PROXY=true` and non-TLS
database URLs (`config.ts:259-285`), the fail-closed database-role check (`db/client.ts:174-179`), the `CONTENT_SOURCE`
default (`config.ts:362-363`). Today's host is fine (HSTS observed), but a fresh install from the templates, or a lost
drop-in, silently loses all of them and would accept `AUTH_MODE=mock` from the environment.
_Fix._ `Environment=NODE_ENV=production` in both unit templates and the rendered units; `example.env` ships
`NODE_ENV=production` with a dev comment; `config.ts` refuses (not defaults) when `API_HOST` is non-loopback or
`PUBLIC_BASE_URL` is https and `NODE_ENV` is not `production`. Tests: `tests/unit/deploy/service-account.test.ts`
asserts rendered units carry it; `tests/unit/api/config.test.ts` asserts the refusal.

**S-02 · Datasource `headers` are not filtered**
`portal/apps/api/src/datasources/executor.ts:248-254` `cleanHeaders` drops only empty values. The engine's
equivalent refuses `authorization|cookie|proxy-authorization|host|x-ms-client-request-id|client-request-id`
(`packages/engine/src/handlers.ts:30-31`). The HTTP client spreads caller headers **after** the bearer
(`packages/connectors/src/http.ts:299-307`), so a page datasource declaring `headers.Authorization` relays Graph reads
under a Reader-supplied token while audit attributes them to the session user, and a spoofed correlation id is what
Microsoft logs. Policy still applies, so no privilege gain against the tenant; the identity attribution of outbound
calls is what breaks.
_Fix._ Apply the same forbidden-header list in `cleanHeaders` and, as the choke point, strip those names in
`createHttpClient` before adding `Authorization`. Tests: a datasource with `headers.Authorization` is refused; caller
`Authorization` cannot replace the bearer.

**S-03 · The publish-time injection lint has blind spots** (confirmed with a `tsx` probe)
`portal/packages/expressions/src/validate.ts:180-204`: `$`-rooted paths are followed through function calls, but
named roots (`params`, `inputs`, `row`) are recognised bare only, and block aliases bind `$`-rooted expressions only.
These all pass: `startswith(displayName,'${ $lowercase(params.q) }')`, `$string(params.q)`, `$join([params.q])`,
`($q := params.q; $q)`, `$map(params.ids,…)[0]`, an `$expand` containing `'${ params.q }'`, and
`/users/${ $trim(params.id) }`. A content author writing an innocent `$lowercase(params.q)` lets any Reader rewrite
the page's OData or KQL filter within their own delegated read scope (path still cleaned, policy still default-deny).
It is scope widening of a page, not escalation; the issue is that the documented gate does not gate.
_Fix._ Treat user-data roots like `$`-rooted paths (follow through non-encoder functions, lambdas and block aliases);
lint `$expand`; add `ds` to the roots (S-13). Consider a runtime check that `$filter`/`$search` values were produced
by a helper. Test: extend `tests/unit/expressions/odata-lint.test.ts` with the eight probe cases.

**S-04 · No minimum release age for dependencies**
`pnpm-workspace.yaml:7-11` has `allowBuilds` and `overrides` only; `.github/dependabot.yml` has no `cooldown`. A
compromised upstream version can land in a grouped Dependabot PR the day it is published, run in CI, and reach the
host on merge.
_Fix._ `minimumReleaseAge: 10080` (seven days) in `pnpm-workspace.yaml`; Dependabot `cooldown: { default-days: 7 }`;
a tooling unit test asserting the value.

**S-05 · Hostile character reference crashes a page** (confirmed by running the module)
`portal/packages/widgets/src/lib/text.ts:33-34` decodes numeric entities with `String.fromCodePoint` and no range
check; `toText('<b>&#1114112;</b>')` throws `RangeError`. Rendered synchronously by the list, timeline and status-grid
widgets with no per-widget error boundary, so the router's error view replaces the whole `/p/<key>` page. Anyone who
can set a displayed string in the tenant (an app owner's app name, a group description) takes the page down for every
engineer until the value changes.
_Fix._ Reuse the server's guard (`api/src/news/text.ts:40-43`: refuse n ≤ 0, n > 0x10FFFF and surrogates) and wrap
each block in an error boundary inside `WidgetPanel`. Tests: the four payloads render as text; a list with one hostile
row still renders the others.

**S-35 · Read-only PowerShell policy ignores file redirection**
`portal/apps/runner/ps/AdminForge.Runner/ReadOnlyPolicy.ps1:202-318` walks Command, Member, Type, Variable, Using,
TypeDefinition and Dynamic nodes; there is no `FileRedirectionAst` case and the word "redirect" does not occur in the
file. `Out-File`, `Set-Content`, `Add-Content` and `Export-*` are refused as commands, leaving `>`, `>>`, `2>` and `*>`
as an uninspected write path. A read-mode script that passes review can still write files into the runner's writable
paths (`StateDirectory`, `PrivateTmp`; the disk is at 94 %). `ProtectSystem=strict` keeps code paths read-only, so no
persistence, and the data written is only what the script could already read; but read mode is the layer meant to
hold when review misses something.
_Fix._ Add `FileRedirectionAst` and merging redirections to a file to the switch with the message "Read-only scripts
can't redirect output to a file". Test: add `Get-Date > out.txt`, `>>`, `2>` and `*>` to the refused list in
`tests/runner/pester/ReadOnlyPolicy.Tests.ps1`.
