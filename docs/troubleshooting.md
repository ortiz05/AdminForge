# Troubleshooting and error reference

For people using AdminForge and for portal administrators. Every error in AdminForge says what happened, what to do
next, and shows a **Reference**. This page lists the codes behind those messages and what fixes them.

Related: `docs/access.md` (roles and groups), `docs/operations.md` (running the host), `SECURITY.md` (security model),
`portal/deploy/README.md` (installation).

## The Reference

Every error shows a Reference: in a toast, an error panel, a run page ("Correlation ID"), or under **Details for your
administrator** on the sign-in problem page. It is the request's correlation id (a UUID). The API also returns it in
the `x-correlation-id` response header and sends it to Microsoft as `client-request-id` (Graph) or
`x-ms-client-request-id` (Azure Resource Manager).

**Users:** select **Copy details** (problem page) or copy the Reference and send it to a portal administrator with
the time it happened.

**Administrators** find it here:

| Where            | How                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API log          | `journalctl --user -u adminforge-api \| grep <reference>`. Log lines are JSON with the Reference as `reqId`; refused requests are logged at `info` as "request rejected" (with `code` and `status`), failures at `error` with the stack.                                                                                                                            |
| Audit page       | `/audit` (needs `Portal.Admin`). Filter by **Who**, **Action** (for example `session.*` or `run.*`) and date; each event's detail shows its Correlation ID.                                                                                                                                                                                                         |
| Database         | `select ts, actor_upn, action, result, details from audit_events where correlation_id = '<reference>';` (column `correlation_id` in `audit_events`).                                                                                                                                                                                                                |
| Microsoft logs   | Microsoft receives the same id as the client request id: Azure activity log entries show it, and you can quote it (with Microsoft's request-id from the error hint) in Microsoft support tickets.                                                                                                                                                                   |
| Sign-in failures | Failed sign-ins are audited as `session.signin` with `result = failure`; failed arming as `session.armed`. `details` holds the AdminForge code, the AADSTS number and Entra's own description (which the person never sees). Failures before the response is matched to a pending sign-in or session (`invalid_state`, `session_mismatch`) are only in the API log. |

## Sign-in and write access

When a sign-in or write-access round trip fails in the browser, the API redirects to the public page
`/sign-in-problem`. It shows a title, what happened, what to do next, buttons (**Sign in again**, **Use a different
account**, **Back to AdminForge**), and **Details for your administrator**: Error code, Microsoft code (the AADSTS
number, or the OAuth error such as `access_denied`), Reference and Time. Entra's raw error text is never shown. Codes
without their own text get a general explanation.

Sign-in requests are limited to 30 a minute per browser address, write-access requests to 10.

### Turning on write access (arming)

Arming signs in again to the AdminForge **Write** app. With `WRITE_AUTH_CONTEXT` set, a Conditional Access
authentication context must be satisfied; without it, Microsoft must ask for credentials again and the sign-in must be
at most 5 minutes old. Every failure leaves the person signed in with read-only access ("You’re still signed in with
read-only access").

| Code                                                             | What it means                                                                                                                                              | What the user does                                                                                      | What an admin does                                                                                                                                                                          |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `no_write_access`                                                | "Your account can’t turn on write access". Entra refused the Write app sign-in (AADSTS50105): only the Operator group is assigned to it.                   | Ask for the Operator role.                                                                              | Add the account to `SG-AdminForge-<label>-Portal.Operator`.                                                                                                                                 |
| `forbidden`                                                      | Same page: the session doesn't have `Portal.Operator` (for example it was removed while verifying).                                                        | Ask for the Operator role.                                                                              | Add the account to `SG-AdminForge-<label>-Portal.Operator`.                                                                                                                                 |
| `consent_required`                                               | "Write access isn’t approved in your organisation yet": the Write app has no consent (AADSTS65001, 65004).                                                 | Ask a Global Administrator.                                                                             | Run `pnpm adminforge provision entra`.                                                                                                                                                      |
| `step_up_required`                                               | "Your verification didn’t meet the write-access policy". `WRITE_AUTH_CONTEXT` is set and the token doesn't show that authentication context was satisfied. | Arm again and complete every prompt (for example on a compliant device or with phishing-resistant MFA). | Check the Conditional Access policy that targets the authentication context named in `WRITE_AUTH_CONTEXT`, and the Write app sign-in in the Entra sign-in logs.                             |
| `step_up_stale`                                                  | "Write access needs a fresh verification". No authentication context is configured and Microsoft reused a sign-in older than 5 minutes.                    | Arm again and enter your credentials when Microsoft asks.                                               | Usually nothing. If it repeats for everyone, check the host clock: the sign-in time is compared with server time.                                                                           |
| `step_up_unverified`                                             | "AdminForge couldn’t confirm your verification". The Write app token has no `auth_time` claim, so write access stays off (fails closed).                   | Ask a portal administrator, then arm again.                                                             | Run `pnpm adminforge provision entra`; it adds the `auth_time` claim to the Write app.                                                                                                      |
| `user_mismatch`                                                  | "You verified with a different account" than the one signed in.                                                                                            | Arm again and verify with the account shown in the top-right corner.                                    | Nothing.                                                                                                                                                                                    |
| `session_mismatch`                                               | "Your session changed while you were verifying", for example after signing in again in another tab, or the session ended.                                  | Go back to AdminForge and arm again from that tab.                                                      | Nothing.                                                                                                                                                                                    |
| `invalid_state`                                                  | "This write-access request has expired": verification must finish within 10 minutes, in the tab that started it.                                           | Arm again.                                                                                              | As for sign-in.                                                                                                                                                                             |
| `arm_cancelled`                                                  | "Write access wasn’t turned on": the verification was cancelled.                                                                                           | Arm again when ready.                                                                                   | Nothing.                                                                                                                                                                                    |
| `blocked_by_policy`, `entra_unavailable`, `rate_limited`         | As for sign-in.                                                                                                                                            | As for sign-in.                                                                                         | As for sign-in.                                                                                                                                                                             |
| `arm_failed`, `wrong_tenant`, `invalid_request`, `invalid_nonce` | General page "Write access wasn’t turned on".                                                                                                              | Arm again; if it repeats, send the details.                                                             | Look up the Reference in the API log ("write code redemption failed" means AdminForge couldn't redeem the sign-in: check the Write app credential with `pnpm adminforge provision status`). |

These arm errors appear in the portal (Arm dialog or a toast), not on the problem page:

| Code                       | Meaning and fix                                                                                                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `write_app_not_configured` | Write access isn't set up on this installation. Admin: run `pnpm adminforge provision entra` (writes `AF_WRITE_CLIENT_ID` / `AF_WRITE_CLIENT_SECRET`), restart the API. |
| `forbidden`                | Arming needs `Portal.Operator`. The message names the group to join.                                                                                                    |
| `not_armed`                | Extending: write access is already off. Arm again.                                                                                                                      |
| `already_extended`         | The write window can be extended once. Disarm, then arm again to start a new window.                                                                                    |

### Sessions

Sessions end after 60 minutes idle or 12 hours in total (`SESSION_IDLE_MINUTES`, `SESSION_ABSOLUTE_HOURS`). Only
what the person does counts as activity: a tab left open (polling, live updates) doesn't keep the session alive, and
when it ends the tab shows "You're signed out" with **Sign in again** instead of signing in by itself. Roles are
re-read from Entra every 5 minutes — by the portal and by the run worker for unattended runs: added roles apply, a
session with no AdminForge role left ends, and losing Operator ends write access at once. The write window is
`WRITE_SESSION_MAX_MINUTES` (default 60) with one extension.

## Errors inside the portal

Portal errors show the message, the next step and the Reference. Codes come from the API (`portal/apps/api/src`).

### Session and requests

| Code               | Meaning and fix                                                                                                                                                                                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `unauthenticated`  | The session ended (idle, expired, or signed out elsewhere). The portal opens sign-in automatically.                                                                                                                                                                                        |
| `reauth`           | Microsoft wants a fresh sign-in (sign-in frequency, Conditional Access, revoked tokens). The portal opens sign-in automatically; nothing was changed.                                                                                                                                      |
| `csrf`             | The page is out of date with the sign-in (for example after signing in in another tab). The portal refreshes the token and retries once; otherwise reload the page. Nothing was changed.                                                                                                   |
| `rate_limited`     | Too many requests from this session this minute (`RATE_LIMIT_PER_MINUTE`, default 600; background requests `RATE_LIMIT_BACKGROUND_PER_MINUTE`; report downloads 60), or from one network address across all sessions (`RATE_LIMIT_PER_ADDRESS_PER_MINUTE`, default 20,000). Wait a minute. |
| `invalid_request`  | The request wasn't valid; the message names the field. Fix the value and retry.                                                                                                                                                                                                            |
| `not_found`        | No such route. Usually an old bookmark: start from the navigation.                                                                                                                                                                                                                         |
| `too_many_streams` | More than 5 AdminForge tabs (live-update streams) are open in this session. Close some tabs; the others keep updating.                                                                                                                                                                     |

### Microsoft services

The hint says what's missing and includes Microsoft's request-id when there is one.

| Code                   | Meaning and fix                                                                                                                                                                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `upstream_forbidden`   | Microsoft refused (401/403). Usually your own Entra role (activate it in PIM if eligible) or Azure RBAC role; otherwise a permission the AdminForge app lacks. Admin: `pnpm adminforge validate --scopes`, then `pnpm adminforge provision entra`. |
| `licence_required`     | The tenant's licences don't include this feature; the message or hint names the licence. Nothing AdminForge can fix; record gaps in `docs/licensing-review.md`.                                                                                    |
| `upstream_not_found`   | Not found: deleted or renamed, or the feature isn't available in this tenant. Refresh and try again.                                                                                                                                               |
| `upstream_bad_request` | Microsoft rejected the request. Check the filter and search values.                                                                                                                                                                                |
| `throttled`            | Microsoft is throttling. Wait a minute.                                                                                                                                                                                                            |
| `upstream_unreachable` | The service couldn't be reached (network problem or timeout). Try again shortly.                                                                                                                                                                   |
| `outbound_busy`        | Every outbound slot for Microsoft calls stayed taken for `OUTBOUND_QUEUE_WAIT_MS` (default 15 s). Try again in a moment. Admin: if it recurs, the outbound limits are too low for the load (Operations → Sizing).                                  |
| `datasource_timeout`   | The data took longer than `DATASOURCE_DEADLINE_MS` (default 2 minutes) to load, every page and retry included, so AdminForge stopped. Narrow the filters (a shorter date range, a search, a facet) and try again.                                  |
| `upstream_error`       | Microsoft returned an error, or a paging link pointed outside the service (refused). Try again; if it persists, send the Reference.                                                                                                                |
| `invalid_cursor`       | The paging cursor doesn't match this data. Reload the list.                                                                                                                                                                                        |

### Synthetic monitoring

Probe tiles show a status and the latest message; the codes below appear in the probe's results and on the
schedule's run (`/monitoring`, or `/monitoring?group=<service>` for one service).

| Code                 | Meaning and fix                                                                                                                                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `not_configured`     | The setting the probe needs isn't set (the message names it, e.g. `AF_SYNTHETIC_MAILBOX`), or isn't a mailbox address / Graph site id / object id. Synthetic transactions do nothing until set (docs/operations.md).        |
| `forbidden`          | Microsoft refused the identity. For a transaction the message names what to assign: the Exchange role and scope, the site grant, or the Teams application access policy; otherwise run `pnpm adminforge validate --scopes`. |
| `not_delivered`      | The mail flow test message didn't reach the test mailbox in time. Check Exchange service health, the sender's outbound limits and transport rules; the result's Exchange timing says whether it arrived late.               |
| `junk`               | The test message landed in Junk Email: delivery works, filtering doesn't trust the sender. Check SPF, DKIM and DMARC for its domain and the anti-spam policies.                                                             |
| `cleanup_failed`     | The check worked but its test item stayed (message, file or meeting): the identity can create but not delete. Grant read-write (not only send/create); the next run removes leftovers it recognises.                        |
| `expectation_failed` | The service answered, but not as expected — another status, missing text, a different file back from SharePoint, a meeting without a join link.                                                                             |
| `writes_paused`      | The emergency stop is on, so synthetic transactions pause with every other change. Read-only checks keep running.                                                                                                           |
| `protected_object`   | A synthetic transaction's test object is a protected account (`AF_PROTECTED_USER_IDS`), so nothing was sent. Point `AF_SYNTHETIC_*` at a dedicated test object.                                                             |
| `schedule_disabled`  | **Run now** on a schedule that runs synthetic transactions while it is turned off. Turn it on first, once its test objects are set up.                                                                                      |
| `insufficient_data`  | Too few sign-ins (or rows) in the window to judge; shown as healthy. Small tenants see this for the per-workload sign-in checks.                                                                                            |

| `schedule_limit`                        | Portal report schedules: 25 active per person, 200 in total, 50 created per person in 24 hours (deleted ones count). Delete ones nobody needs; move long-lived ones into content.                                                                            |
| `schedule_is_content`                   | The schedule is defined in content: change its YAML and publish it. Any Operator can still turn it off or run it now.                                                                                                                                        |
| `report_cannot_change`                  | A schedule always runs the same report. Schedule the other report from Reports and delete this schedule.                                                                                                                                                     |
| `schedule_changed`                      | Someone saved or deleted the schedule at the same moment. Reload it and try again.                                                                                                                                                                           |
| `forbidden` (edit/delete)               | Only the person who created a portal schedule, or a `Portal.Admin`, can edit or delete it. Any Operator can turn it off.                                                                                                                                     |
| `run_too_soon`                          | Run now on a portal schedule waits while a run is queued or running and for 15 minutes after the last manual run. Try again later, or open the latest file in its history.                                                                                   |
| `creator_access_removed`                | The person who created this portal schedule lost access (account deleted, disabled, now a guest, or a role removed), so it was turned off. Schedule the report again from Reports.                                                                           |
| `creator_unverified`                    | AdminForge couldn't confirm the creator still has access, so that run didn't happen. Admin: the automation identity needs User.Read.All, GroupMember.Read.All and Application.Read.All.                                                                      |
| `report_incomplete`                     | The report file was written and sent, but an optional part of it (named in the message) couldn't be read — usually a permission or licence the automation identity lacks (`pnpm adminforge validate --scopes`). The run is marked failed so it isn't missed. |

Schedule run history can also show `timeout` (the job exceeded its timeout, default 15 minutes), `interrupted` (the
scheduler stopped mid-run), `no_probes` (no active probe matches the job), `probes_errored` (no probe could be
evaluated; see each probe's message — a job whose probes are all only "not configured" succeeds instead, with a
note), `run_failed` (the scheduled playbook run failed; open the run) and
`content_unhealthy` (content problems, or permissions the automation identity lacks).

## Report downloads

Scheduled report files open from the Schedules page. When a download fails, the browser lands on the problem page
(labelled "Report download") instead of saving an error as the file.

| Code                 | What the user sees                        | What to do                                                                                                                                                                                                                                          |
| -------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `forbidden`          | "You can’t download this report"          | Reports are collected with AdminForge's own permissions, so they're limited to the roles the schedule names (Operator by default). Admin: add the person to `SG-AdminForge-<label>-Portal.Operator`, or set `requires.portalRoles` on the schedule. |
| `artifact_not_found` | "This report file is no longer available" | Schedules keep a limited number of report files (the newest `retain` per format). Open the schedule and select **Run now** for a fresh copy.                                                                                                        |
| `unauthenticated`    | "Sign in to download this report"         | Sign in, then select the report again.                                                                                                                                                                                                              |
| `rate_limited`       | "Too many downloads this minute"          | More than 60 downloads a minute from this browser. Wait a minute.                                                                                                                                                                                   |
| anything else        | "The report didn’t download"              | Try again from the schedule's run history; if it repeats, send the details.                                                                                                                                                                         |

## News and changes

Feed failures show on `/news` → **Sources** (the reason only for Operators); every code is explained in
`docs/news.md` → Troubleshooting codes.

| Code / symptom                                      | What the user sees                                   | What to do                                                                                                                                      |
| --------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `news_not_found`                                    | "That news item isn’t available"                     | It aged out, or it needs a role the person doesn't have (data-privacy Message Center posts are Portal.Admin only). Open News and changes again. |
| `invalid_request` on `/api/news`                    | "The News and changes filters aren’t valid"          | The hint names the filter; reset the filters.                                                                                                   |
| Empty page, "The first collection runs on the hour" | No feed has been collected yet                       | Operator: Schedules → News and changes refresh → Run now; check the scheduler is running.                                                       |
| A feed is _stale_ or shows an error                 | Its last collection failed or hasn't run for 3 hours | Operator: read the code under Sources and follow `docs/news.md`; tenant feeds need the automation app's permissions (`provision status`).       |
| A source says "no new posts since …"                | The source itself has gone quiet (`quietAfterDays`)  | Nothing to fix in AdminForge; consider retiring the feed (see `docs/backlog.md`).                                                               |

## Operations symptoms

Service names, logs and files are in `docs/operations.md`.

| Symptom                                                                                                            | Check                                                                                       | Fix                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A service doesn't start or keeps restarting                                                                        | `systemctl --user status adminforge-<name>`, `journalctl --user -u adminforge-<name> -n 50` | "Invalid AdminForge configuration" lists the offending keys (never values): fix them and run `pnpm adminforge env check`. Worker and scheduler exit without `DATABASE_URL`; the runner without `RUNNER_SHARED_KEY`. If `node` isn't found, add its bin directory to `Environment=PATH=` (`portal/deploy/README.md`).                                                                                                      |
| Services stop when you log out                                                                                     | `loginctl show-user "$USER" -p Linger`                                                      | `loginctl enable-linger "$USER"`.                                                                                                                                                                                                                                                                                                                                                                                         |
| Postgres is down: `/readyz` answers 503 `not_ready`, CLI says "Can't connect"                                      | `curl -s http://127.0.0.1:3300/readyz`, `docker ps`                                         | `pnpm db:up`, then check `DATABASE_URL`. CLI commands print the fix on one line (connection refused → `pnpm db:up`; wrong password; missing database → `pnpm --filter @adminforge/api db:migrate`); add `ADMINFORGE_DEBUG=1` for the stack.                                                                                                                                                                               |
| Exchange, Teams or SharePoint pages and steps fail (`runner_*`)                                                    | `systemctl --user status adminforge-runner`; its journal should say "runner ready"          | Start or restart the runner. Its health check is a signed `GET /healthz`: in `portal/apps/runner`, `node dist/healthcheck.js` exits 0 when healthy (needs `RUNNER_SHARED_KEY` in the environment). "degraded" means missing pinned modules or failed preloads: `pnpm --filter @adminforge/runner modules:install`; `PWSH_PATH` must point at `pwsh`.                                                                      |
| Schedules don't fire                                                                                               | `journalctl --user -u adminforge-scheduler \| grep -i leader`                               | "elected leader": this scheduler is active; check that the schedule is enabled (new ones start disabled), approved if it writes, and that the automation identity is configured. Only "standing by for the leader lock": another scheduler on the same database holds the advisory lock, for example `pnpm dev` with `SCHEDULER_IN_PROCESS=true` (next row). A tick missed by more than an hour is skipped, not run late. |
| `pnpm dev` picks up the services' runs or schedules, or the host scheduler only stands by                          | Do the dev server and the services use the same `DATABASE_URL`?                             | They must not. Give the services their own `DATABASE_URL` in `<env>.host.env` and set `Environment=ADMINFORGE_ENV_OVERLAY=host` in the api, worker and scheduler drop-ins (layering: `config/example.env` header). Run CLI commands meant for the services with the overlay, e.g. `ADMINFORGE_ENV_OVERLAY=host pnpm adminforge publish`.                                                                                  |
| Runs stay queued                                                                                                   | `systemctl --user status adminforge-worker`                                                 | Start the worker. In `pnpm dev` (own database) set `RUN_WORKER_IN_PROCESS=true` instead.                                                                                                                                                                                                                                                                                                                                  |
| A content change doesn't show up                                                                                   | The services serve published content (`CONTENT_SOURCE=db`)                                  | `pnpm adminforge validate`, then `ADMINFORGE_ENV_OVERLAY=host pnpm adminforge publish`. "refused" means that version is already published with different content: bump `version`.                                                                                                                                                                                                                                         |
| The browser warns about the certificate on the LAN address                                                         | Caddy issues certificates from its own CA (`tls internal`)                                  | Trust Caddy's root certificate (`~/.local/share/caddy/pki/authorities/local/root.crt`) on each client: `portal/deploy/README.md`, `docs/operations.md`.                                                                                                                                                                                                                                                                   |
| Sign-in always ends on "This sign-in link has expired", or Microsoft reports a redirect URI mismatch (AADSTS50011) | Compare the address bar with the API service's `PUBLIC_BASE_URL`                            | Sign-in works only on the `PUBLIC_BASE_URL` origin: redirect URIs are built from it and cookies are per origin. Use that address, on the host too. To add an address: put it in `AF_REDIRECT_BASE_URLS`, run `pnpm adminforge provision entra`, set `PUBLIC_BASE_URL` in the api, worker and scheduler drop-ins, restart. Non-localhost addresses must be HTTPS.                                                          |
| Many people get `rate_limited` at once                                                                             | `TRUST_PROXY` for the API                                                                   | Keep the default `loopback` (Caddy on this host): with `false`, every browser shares Caddy's address and one rate limit.                                                                                                                                                                                                                                                                                                  |
| Everyone has to sign in again after a restart                                                                      | Was `TOKEN_CACHE_KEY` changed?                                                              | Expected after rotating it: the sealed token cache can't be read with a new key. Nothing else is lost.                                                                                                                                                                                                                                                                                                                    |
