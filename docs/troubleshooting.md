# Troubleshooting and error reference

For people using AdminForge and for portal administrators. Every error in AdminForge says what happened, what to do
next, and shows a **Reference**. This page lists the codes behind those messages and what fixes them.

Related: `docs/access.md` (roles and groups), `docs/operations.md` (running AdminForge), `SECURITY.md` (security
model), `portal/deploy/kubernetes/README.md` (installation).

## The Reference

Every error shows a Reference: in a toast, an error panel, a run page ("Correlation ID"), or under **Details for your
administrator** on the sign-in problem page. It is the request's correlation id (a UUID). The API also returns it in
the `x-correlation-id` response header and sends it to Microsoft as `client-request-id` (Graph) or
`x-ms-client-request-id` (Azure Resource Manager).

**Users:** select **Copy details** (problem page) or copy the Reference and send it to a portal administrator with
the time it happened.

**Administrators** find it here:

| Where            | How                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API log          | `kubectl -n adminforge logs deploy/adminforge -c api \| grep <reference>` (recent lines; older ones in the log store you ship them to). Log lines are JSON with the Reference as `reqId`; refused requests are logged at `info` as "request rejected" (with `code` and `status`), failures at `error` with the stack.                                               |
| Audit page       | `/audit` (needs `Portal.Admin`). Filter by **Who**, **Action** (for example `session.*` or `run.*`) and date; each event's detail shows its Correlation ID.                                                                                                                                                                                                         |
| Database         | In a copy of the database (`adminforge db backup`, opened with `sqlite3`): `select datetime(ts / 1000, 'unixepoch'), actor_upn, action, result, details from audit_events where correlation_id = '<reference>';`                                                                                                                                                    |
| Microsoft logs   | Microsoft receives the same id as the client request id: Azure activity log entries show it, and you can quote it (with Microsoft's request-id from the error hint) in Microsoft support tickets.                                                                                                                                                                   |
| Sign-in failures | Failed sign-ins are audited as `session.signin` with `result = failure`; failed arming as `session.armed`. `details` holds the AdminForge code, the AADSTS number and Entra's own description (which the person never sees). Failures before the response is matched to a pending sign-in or session (`invalid_state`, `session_mismatch`) are only in the API log. |

## Sign-in and write access

When a sign-in or write-access round trip fails in the browser, the API redirects to the public page
`/sign-in-problem`. It shows a title, what happened, what to do next, buttons (**Sign in again**, **Use a different
account**, **Back to AdminForge**), and **Details for your administrator**: Error code, Microsoft code (the AADSTS
number, or the OAuth error such as `access_denied`), Reference and Time. Entra's raw error text is never shown. Codes
without their own text get a general explanation.

Sign-in requests are limited to 300 a minute per network address (`RATE_LIMIT_SIGNIN_PER_ADDRESS_PER_MINUTE`; behind a
NAT everyone shares one), write-access requests to 10 a minute per session.

### Turning on write access (arming)

Arming signs in again to the AdminForge **Write** app. With `WRITE_AUTH_CONTEXT` set, a Conditional Access
authentication context must be satisfied; without it, Microsoft must ask for credentials again and the sign-in must be
at most 5 minutes old. Every failure leaves the person signed in with read-only access ("You’re still signed in with
read-only access"). Arming gives the session a new id: other open tabs reconnect their live updates by themselves, and
a run started before arming pauses before its next change ("Paused: check this run is yours, then resume it") until
the person checks it and selects **Resume run**.

| `no_write_access`                                                | "Your account can’t turn on write access". ### Sessions

Sessions end after 60 minutes idle or 12 hours in total (`SESSION_IDLE_MINUTES`, `SESSION_ABSOLUTE_HOURS`). Only
what the person does counts as activity: a tab left open (polling, live updates) doesn't keep the session alive, and
when it ends the tab shows "You're signed out" with **Sign in again** instead of signing in by itself. Roles are
re-read from Entra every 5 minutes — by the portal and by the run worker for unattended runs: added roles apply, a
session with no AdminForge role left ends, and losing Operator ends write access at once. The write window is
`WRITE_SESSION_MAX_MINUTES` (default 60) with one extension.

## Errors inside the portal

Portal errors show the message, the next step and the Reference. Codes come from the API (`portal/apps/api/src`).

### Session and requests

| Code                     | Meaning and fix                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unauthenticated`        | The session ended (idle, expired, or signed out elsewhere). The portal opens sign-in automatically.                                                                                                                                                                                                                                                                                                             |
| `reauth`                 | Microsoft wants a fresh sign-in (sign-in frequency, Conditional Access, revoked tokens). The portal opens sign-in automatically; nothing was changed.                                                                                                                                                                                                                                                           |
| `csrf`                   | The page is out of date with the sign-in (for example after signing in in another tab). The portal refreshes the token and retries once; otherwise reload the page. | `rate_limited`           | Too many requests from this session this minute (`RATE_LIMIT_PER_MINUTE`, default 600; background requests `RATE_LIMIT_BACKGROUND_PER_MINUTE`; report downloads 60), or from one network address across all sessions (`RATE_LIMIT_PER_ADDRESS_PER_MINUTE`, default 20,000). Wait a minute.                                                                                                                      |
| `invalid_request`        | The request wasn't valid; the message names the field and what it must be ("format must be csv or xlsx"). | `too_many_streams`       | More than 5 AdminForge tabs (live-update streams), or more than 5 open run pages, in this session. | "Needs review: a step may or may not have happened"                | A step that can't be retried safely (`idempotent: false`) was in flight when the worker stopped (a crash, or a restart that outlasted the 10 s grace). | Needs review: "… and the check … before it no longer holds"        | A change was in flight when the worker stopped (or was sent before the run stopped), and the check run again before sending it once more no longer holds — perhaps because the first send went through. | Failed: "… so this was checked again first"                        | The run had paused (an approval, input, write access, a sign-in, a restart), and before its next change it read and checked again; the check named in the message no longer holds, so nothing more was sent. | "Only … can see the inputs and results"                            | Someone else's run: it ran with that person's own access, so you see what ran, who, when and its status, not its inputs, results, logs or error details (only the error code). | A content change doesn't show up                                                                                                                                              | The pod serves published content (`CONTENT_SOURCE=db`) from its image                                                            | Deploy an image built from the change, then `kubectl -n adminforge exec deploy/adminforge -c api -- adminforge publish` (`docs/operations.md` → Content changes). "refused" means that version is already published with different content: bump `version`.                                                                                                                                                                  |
| Live updates never arrive or stop after a while (run pages, the event dock)                                                                                                   | The ingress controller's buffering and timeouts                                                                                  | Server-Sent Events must pass unbuffered and stay open: with ingress-nginx, `proxy-buffering: off` and long read and send timeouts (the example overlay's `ingress.yaml`); other controllers need their equivalent.                                                                                                                                                                                                           |
| The browser warns about the certificate                                                                                                                                       | The Ingress certificate (`adminforge-tls`)                                                                                       | Expired, for another host name, or from a CA the browser doesn't trust: renew or replace it (`docs/operations.md` → Certificates), or trust your private CA's root on the clients.                                                                                                                                                                                                                                           |
| Sign-in always ends on "This sign-in link has expired", or Microsoft reports a redirect URI mismatch (AADSTS50011)                                                            | Compare the address bar with `PUBLIC_BASE_URL` in the env file the Secret is made from                                           | Sign-in works only on the `PUBLIC_BASE_URL` origin: redirect URIs are built from it and cookies are per origin. Use that address. To add an address: put it in `AF_REDIRECT_BASE_URLS`, run `pnpm adminforge provision entra`, set `PUBLIC_BASE_URL`, update the Secret. Non-localhost addresses must be HTTPS.                                                                                                              |
| Many people get `rate_limited` at once                                                                                                                                        | `TRUST_PROXY` (the overlay's ConfigMap)                                                                                          | Set it to the ingress controller's pod network: otherwise every browser shares the controller's address and one rate limit. Never `true` (production refuses it).                                                                                                                                                                                                                                                            |
| Everyone has to sign in again after a restart                                                                                                                                 | Was `TOKEN_CACHE_KEY` changed, or the database restored from a logical copy?                                                     | Expected after rotating the key without the old one (the sealed token cache can't be read with a new key) and after a restore from `adminforge db backup` (it holds no sessions or tokens). Nothing else is lost.                                                                                                                                                                                                            |
| The pod keeps restarting; the API log says "The audit log is keyed from event seq … but AUDIT_CHAIN_KEY is not set"                                                           | The Secret (`adminforge-env`): was `AUDIT_CHAIN_KEY` removed or emptied?                                                         | Put the installation's key back in the Secret and restart. Once set, the key can be rotated (the old one in `AUDIT_CHAIN_PREVIOUS_KEYS`) but not removed. If it is lost, set a new one and put the lost key's id in `AUDIT_CHAIN_LOST_KEY_IDS` — only an id an "audit chain cut-over" line in the shipped log names: a new keyed part starts, and the events the lost key keyed can no longer be verified.                   |
| The audit-chain check reports `audit_chain_key_missing`, or `adminforge audit verify` says "can't be verified … key id …"                                                     | `AUDIT_CHAIN_PREVIOUS_KEYS` in the Secret (after a key rotation)                                                                 | Put the earlier key back in `AUDIT_CHAIN_PREVIOUS_KEYS` and restart. If no key with that id was ever configured, the cut-over event was forged: snapshot the volume as evidence and investigate who had write access to it.                                                                                                                                                                                                  |
| The API log shows a new "audit chain cut-over" line, but nobody changed `AUDIT_CHAIN_KEY`                                                                                     | The Secret's history; the previous cut-over line in your log store                                                               | A cut-over is expected once per new key. Without a key change, the keyed events were removed from the database: `adminforge audit verify --checkpoint <seq>:<hash>` with the previous cut-over line, then snapshot the volume as evidence and restore from a backup (docs/operations.md → Audit chain checkpoints).                                                                                                          |
| The pod keeps restarting; the API log says "The audit log should be keyed from event seq … (AUDIT_CHAIN_KEYED_SINCE), but that event is not the cut-over"                     | Whether a backup from before the key was set was restored                                                                        | Otherwise the keyed events were removed or rewritten: keep AdminForge stopped, snapshot the volume as evidence, restore from a backup and investigate who had write access to the volume. After restoring a backup from before the key was set, remove `AUDIT_CHAIN_KEYED_SINCE` (a new cut-over follows; pin its seq again).                                                                                                |
